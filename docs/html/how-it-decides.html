Every decision Merit Order makes, in the order it makes them, with the exact rules and defaults. Each rule names the setting that controls it. A request, start to finish

Checks run in this order. The first one that fails ends the request with the error shown.

Which model

The classifier (rules, no model call; routing.levels, Config → Routing → How requests get a level, shown to everyone under Reports → Levels):

Request Floor Setting
Has tools or code-like text (code fences, def, import, file names, "refactor", "bug", SQL, …) coding:3 coding, coding_words
…and simple wording, nothing harder (write tests, rename, typo, lint, docstring, explain, bump, …) coding:2 simple, simple_words
…and "hard" wording (race condition, security, performance, migration, multi-file, "under load", flaky, …) +1 for each distinct match, up to 2; at most 5 hard_raise, hard_signals, hard_words
…and the hardest wording (architecture, "design a", system design, prove, codebase-wide, …) coding:5 hardest, hardest_words
…and the newest prompt says the last answer was wrong ("that's wrong", "revert", …) +1, at most 5 correction_raise
…with 5+ tools, only with agent_by_tools: true (off: tools say it's coding, not how hard) coding:4, simple wording ignored agent_by_tools, agent, agent_tools
Anything else general:2 general
…the whole request under 400 tokens (no tools) general:1 short, short_tokens
…analysis wording (analyze, compare, trade-offs, plan, …) general:3 analysis, analysis_words
X-Route-Hint: cheap / smart −1 / +1
Claude Code side request (x-claude-code-request-class: auxiliary) at most 1 request_class_levels
Claude Code compaction summary (compaction), and the summary the gateway writes for POST /v1/responses/compact at most 3 request_class_levels
X-Route-Floor: coding:4 exactly that, skipping the rules (never capped)
The learned router, in route mode, at least min_confidence (0.8) sure its level instead of the rules' (Claude Code's caps still apply) routing.learned

Wording is looked for in the last two messages from the person: tool results aren't read, and a user message made only of tool results (Anthropic's agent loops send one per step) is passed over, so the prompt behind a task counts mid-task. What the harness adds is left out too: Claude Code's system reminders (CLAUDE.md) and Codex's AGENTS.md and environment context. Where lists overlap, the hardest wins. Coding agents send dozens of tools on every request, so the tool count no longer sets the level (decision 61): "write tests" from Claude Code is coding:2, "fix the race condition" coding:4, "design a plugin system" coding:5. The level is set at a task boundary and held until the next one. The word lists are Python regular expressions, matched ignoring case; a pattern that doesn't compile, or matches empty text and so every request, is refused when the configuration is saved, as is a level outside 1–5.

Length never raises the floor. It only rules out models whose window can't hold the prompt plus the reply (the flowchart above, and the table under Which backend). The one length rule left, the short question, can only lower a level. The routing reason, kept in the ledger and shown under Reports → Requests, names the rules that set the floor and the models ruled out by their windows.

The Claude Code caps are routing.request_class_levels (Config → Routing → Claude Code request types); other classes (main, subagent, workflow) aren't capped. Claude Code sends the header to a gateway only with CLAUDE_CODE_GATEWAY_HINT_HEADERS=1, which meritorder setup claude-code sets. The Responses API's compaction endpoint routes its summary as a compaction request, whichever client called it (04).

The learned router (routing.learned, off by default; 03, Routing) predicts a level next to the rules' wherever they give one, from the request's hashed words and named facts, trained on what followed earlier answers. In shadow mode that's recorded with what it would have picked, and nothing changes; in route mode it's used when it's sure. The rules decide whenever there's no model, the model is stale (older than max_age_days, the level rules changed, or the feature key did), it's under min_confidence, or it fails; a client's X-Route-Floor is never second-guessed. The routing reason says what it predicted, how sure it was, its version, and why it was or wasn't used. It's asked only when an auto request is classified (a new task); a request that names its model only has its features recorded, as training data.

Quality scores (1–5 per task type) come from published benchmarks, refreshed daily (quality:; see 00, How it all works). A model the source doesn't cover isn't a candidate for auto unless it has a quality_override.

Threshold or cost per success

routing.model_choice (or a team's model_choice) sets how auto chooses among models for a new task:

Choice Picks
threshold The cheapest route of a model whose score is at least the level
cost_per_success The lowest expected cost per solved task, among models whose chance of solving work at the level is at least min_success_chance (0.6), whatever their score
expected_cost (default) The lowest expected total cost to finish the task, among the same models: the try, plus the chance of failing times what a failure costs (the person's time the request puts at stake, human_cost_usd scaled by its level and size, and the next attempt); and escalation inside the task (below)

A model's chance at each level comes from its score in use (apply_chances in config.py). The scale says what a score means on the reference work (absolute, the default: 5 × the model's chance ÷ the anchor; best: ÷ the best model's), so a score read back gives its chance there, and a level gives the chance of a model scoring exactly that level. Level-L work is taken to be as much easier than the reference as a model scoring L is weaker than a 5: a model exactly at a level solves that level's work as often as a 5 solves the reference work (the anchor: 69.9% for coding and 76.9% for general, what Claude Fable 5.2 solved of FrontierSWE-hard tasks on 12 November 2026). Every other model sits by its distance from the level on Epoch's logistic ability scale:

chance at level L = sigmoid( logit(chance of its score) − logit(chance of a score of L) + logit(chance of a 5) )

Level 5 is the reference work itself. For coding, that gives:

Model Coding score Level 1 2 3 4 5
Claude Fable 5.2 5.0 97% 93% 88% 81% 70%
Gemini 4 Carbon 4.4 96% 91% 84% 75% 62%
GPT-6.1 Terra 4.2 95% 90% 82% 72% 59%
Claude Sonnet 5.5 3.9 94% 88% 79% 69% 55%
Claude Haiku 5.5 3.0 91% 81% 70% 57% 42%
DeepSeek V4.1 Flash 2.4 88% 75% 62% 48% 34%
GPT-6 Luna 2.3 87% 74% 60% 46% 32%
gpt-oss-20b 1.0 70% 49% 34% 23% 14%

Reading the chance from the score rather than from the published chance keeps the threshold's own rules: an override counts, and the floor of 1 still makes every model fit for level-1 work. Where the chances come from:

Quality source What a 5 solves Scores that get chances
epoch quality.anchor (scale absolute), or the best configured model's published chance on the reference (best) The source's own, and overrides
config quality.measured_best_rate: the best measured model's pass rate on hard eval tasks, written when an eval run's scores are applied as quality The configured scores, and overrides
artificial_analysis Nothing: the index isn't a chance None

A model without a chance (a mock, a score written in the config while a live source is in use, a task type with no measured rate) is judged by the threshold: it's a candidate only at or above the level, and counts at the chance of a model exactly at it. With no chances for the task type at all, the threshold decides.

Expected cost per success. One try costs the route's estimate (below: the session from here, with its warm cache or rebuild) and succeeds with the model's chance at the level. A failed try is still paid for, and the work is then done again on the redo route: the one the threshold would pick (the cheapest route of a model that meets the level; if none does, the most likely to succeed), tried until it succeeds.

redo     = redo route's cost ÷ its chance
expected = cost + (1 − chance) × redo

For the redo route itself that's its cost ÷ its chance. A model below the level wins only when the try it saves on costs less than redoing its extra failures: cost < chance × redo. Failures are assumed independent, and the time a person spends noticing one isn't counted; the minimum chance is what guards against both.

The rules around it:

  • The minimum holds for every model with a chance, at the level too. A model exactly at the level has 70% for coding, so the default 0.6 only rules out models below the level; a minimum above 70% leaves only models above it.
  • The threshold steps in when no model reaches the minimum, or none that does can run right now.
  • A level the client sets (X-Route-Floor, also how a named model is substituted) is a minimum it asked for: the threshold decides.
  • Mid-task the session keeps its model, as always. Cost per success changes where a new task goes, and where a session that outgrew its model moves.
  • Everything after compares expected costs per success: the priority's premium (2%, 20%, 100%), stickiness (a move must save 10% + $0.01), and the speed checks. Cache warmth counts through each route's cost: a warm session's rebuild is zero, so a cheaper model elsewhere has to beat it after paying to rebuild there.
  • Effort and the output limit follow the level, whichever model wins.
  • Teams set their own model_choice and min_success_chance; blank uses the organization's.
  • Levels are untouched: routing.levels still sets them. Reports → Levels shows, for a team routing by cost per success, the models below each level that are in reach, with their chance there.

The routing reason (the ledger's route_reason, shown on Reports → Requests) ends with what it compared: classified coding:3 (coding: 1 tool); cost per success: deepseek-v4.1-flash, expected $0.0051 per success (62% at coding:3) vs $0.0086 (70%) on claude-haiku, the cheapest at the level. When the threshold decides instead, it says why (cost per success: no chances of success for coding, so the threshold decides).

Expected total cost

With model_choice: expected_cost (decisions 62 and 67; 03), the models in reach are the same as cost per success's, and each route is ranked by

E(m)         = try(m) + (1 − P(m)) × (H × stakes + next attempt)
stakes       = (1/3)^(5 − level) × min(1, prompt tokens / 8,000); counted at level 5 after a correction
next attempt = the cheapest of: m again, or a stronger model e (a higher chance) from a cold cache,
               each E(· | m failed) with one attempt fewer left; nothing once max_escalations are planned
Part What it is Setting (default)
try(m) The route's cost for the rest of the session, as above (warm cache or rebuild, the 1-hour cache, pauses)
H What a failed attempt at the top of the scale (a level-5 agent task) costs the person: their minutes times their rate routing.human_cost_usd ($1); team human_cost_usd; Config → Routing → Expected total cost, Controls
stakes The share of H a failure of this request puts at risk: a third for each level below 5 (level 3: 1/9, level 1: 1/81), times the prompt's size up to 8,000 tokens; the whole level-5 share after a correction ("that's wrong", "revert") fixed (success.STAKES_LEVEL, STAKES_TOKENS)
P(m) The benchmark prior at the task's difficulty, read between levels; widened by the learned router's spread in route mode; the fitted layer in its place once it's routing and beat the prior routing.success.mode (off)
A failure's effect on the next attempt Each model's chance on the task moves with a hidden difficulty 1 log-odds wide, so a task one model failed is harder for the next too fixed (success.SPREAD)
Attempts planned after the first None by default: a failure costs the person's time; with the cascade on, as many as it may escalate routing.cascade.max_escalations (0; up to 2)

Inside a task, with the cascade on (routing.cascade.max_escalations 1 or 2; off by default, since on the routing simulator it saved nothing in total, counting failed attempts at a price per failed attempt, for a third more model spend), a team routing by expected_cost may escalate:

When What's compared
Mid-task, after failures_now (3) failures in a row (failed test or build runs, or error tool results) Continuing: the rest of the task on its model, at its chance now (its chance at the task's start moved by the evidence, table in 03), a failure there escalating later. Escalating: the rest of the task on a stronger model from a cold cache, one escalation fewer left. Escalates when that's cheaper by more than switch_margin_usd ($0.01)
At a human message that carries on the task: a correction, or the code left failing (the last run after the last edit failed) and a prompt that, classified first, is the same kind of work at no higher a level than the task's The same; the task, its row and its evidence go on. A correction puts the level-5 share of H at stake, so it's where an escalation most often pays
At any other human message A new task, chosen afresh: the only way a task goes back down

Never for a named model, never past the team's models, never once a budget is 90% spent, never more than max_escalations per task, never into a refusal by max_request_usd. Every request of an escalated task is tagged escalation and escalated_from; its first request (the answer's row, once) takes the failed attempt's baseline cost off its routing savings.

Exploration and the level map

A team that explores (teams.<name>.exploration, off by default) has a few of its task starts routed a level down or up from the level they'd get, at random, so Reports → Levels can say whether each level is too high or too low for the work (03). Before that, a level the outcome report's recommendation moved is applied (routing.level_map, e.g. {"coding:3": 2}).

Arm Its chance (default share 4%, a canary's 20%) Recorded
served 96% (with a canary at the level: 76.8%) arm served, propensity
down, up 2% each (with a canary: 1.6%); at level 1 or 5 the whole 4% one way; up's half stays served near a budget arm, arm_from, propensity, ledger tags explore, explore_from
canary 20% of the level's task starts, until it has 30 there or 14 days pass arm canary

The report weights each task start by 1 ÷ its arm's chance, so arms and teams with different shares compare fairly. A recommendation ("coding level 3: level 2 does as well in 98% (n=412 explored, 9,870 served); consider lowering") needs 200 task starts on each side and a difference clear at 90%; it raises an alert once, and an admin applies it (or the worker, with routing.benchmark.auto_apply, when the learned router's model in use beat the rules and leans the same way).

Which backend: GPU or API

Each candidate model lists its routes (backends that serve it). A route is dropped when:

Dropped when Why
The backend isn't enabled (no key, no URL) or the team may not use it Policy and credentials
The backend is being skipped after failures (see When a backend fails) Bad credentials or a network-level outage: the whole backend. Retried when the wait is up
This model is being skipped on this backend: over capacity (429/503/529), its deployment doesn't exist there (404), or it failed 3 times in a row (408/409/425/500) Only that model there; the backend's other models are unaffected. A busy route is kept as a last resort if nothing else can take the request
It's a GPU deployment that isn't warm (not started, starting, or stopped now) Nothing to send to
It's draining and this session has no warm cache there (on any of its replicas) Draining only finishes sessions already there
It's a GPU at 100% (see When a GPU is full) Saturated: new work spills to other routes. Kept as a last resort if nothing else can take the request
It's a saturated GPU whose queue is also full No room to wait either
auto and the route has no known price An unknown price must never look free
The model's context window is too small (prompt plus the client's max_tokens > 95% of it) and other models fit Avoid a guaranteed error. Mid-task too: a session that outgrows its model moves to one with room, at the same floor. When nothing at the floor fits, only the largest window is kept and the provider decides
auto and it's a mock backend while real ones exist Mocks are for trying things out
A batch request, and the backend has no batch API; or it's a GPU that's full or draining, or batches.gpu.enabled is off Batch work only goes where it can wait at batch prices

The rest are ranked by what this session will cost from here:

cost = rebuild + expected_remaining_turns × per_turn
rebuild   = cached context × (cache-write − cache-read price) × the share of it the backend no longer holds
            (0 when it holds this session's cache; on a GPU, the share is the replica's, see below)
per_turn  = cached context × cache-read + new tokens × cache-write + ~600 output tokens × output price
            (new tokens: ~2,000, or for a known session what the prompt grew since its last turn, at least 200;
             cached context: the rest of the prompt.
             cache-write is the input price except where caching is explicit and writes cost extra:
             Anthropic-format backends (Claude on Anthropic, Bedrock, Vertex, Foundry) and Claude through
             OpenRouter, which gets a cache marker; on a backend whose cache_ttl_seconds is 3600 or more,
             the 1-hour write price. Elsewhere caching is automatic.)
          + after the first turn, where the cache lasts under an hour (cache_ttl_seconds < 3600):
            pause share × cached context × (cache-write − cache-read)
            (a pause of 5 to 60 minutes rebuilds a 5-minute cache, not an hour's; the share is the team's own,
             leaning on the organization's and a prior of 1 in 10, from pauses.py; GPUs get none)
turns     = turns so far, clamped to 3…30 (a long session is expected to keep going)
prices    = the route's live price (or its `price:` override) at this prompt's length (long-prompt tiers apply)

A GPU's price is a shadow price: what one token "costs" given how busy the GPU is. It scales the price: written on the GPU route, which is set to the model's API-equivalent rate (GPUs have no live price list); a GPU route without one is never used by auto.

So GPUs win whenever they have room, even for a better model than the task needs (a "free upgrade", sent at low vLLM priority so traffic that needs that model goes first). As they fill up, APIs win again.

Batch requests are priced the same way against the providers' batch prices (about half): a running GPU with room wins, at its shadow price for its load now. The worker then runs them only in the headroom below the knee (60% of max_concurrency × replicas, less live requests), at vLLM priority 20, below free upgrades, and hands what hasn't run after 12 hours to the request's provider batch route (02).

Then the tie-breakers:

  1. Close on price, then quality and speed. The same model often costs the same everywhere (Claude on Anthropic, Bedrock, Foundry and OpenRouter), so price alone can't choose. Routes that cost at most the priority's premium more than the cheapest compete on speed instead:
Priority A faster route may cost up to Within that range
cost (default) 2% more (a tie) the higher-quality model (auto), then the faster route
balanced 20% more the faster route, then the higher-quality model
speed 100% more the faster route, then the higher-quality model

With expected total cost the range is the premium of the cheapest route's money (the tokens in its expected total), not of its total with the person's time, so a 2% tie stays 2% of what's spent (decision 67). The organization default is routing.priority; a team can set its own (priority), and a request can send X-MeritOrder-Priority: cost|balanced|speed. Speed is the expected time for a typical reply (routing.est_output_tokens, 600 tokens): time to the first token plus the writing time, both moving averages of real replies on that route (backend + upstream model). Timing starts when the route is called, so a route that took over after a failure isn't charged for it. A route is trusted after 2 replies; until then it ranks after measured ones, keeping cost order. 2. Measuring the alternatives. Otherwise the first route measured would win forever. Every 10th new session (routing.speed_check_every; 0 turns it off) can go to a route in that price range that hasn't been measured, or not in the last 10 minutes. Never mid-session, so no cache is lost. 3. Stickiness: a session stays on its current backend unless the cheapest one saves more than 10% + $0.01 over the rest of the session (with expected total cost, the difference in expected totals has to beat 10% of the current route's money plus $0.01), which is usually only true once its cache has expired (as long as the request's last cache marker asked: 5 minutes, or an hour for the gateway's own markers from a session's second turn on the shipped Claude backends; cache_ttl_seconds per backend). That's what stops a session bouncing between Bedrock and Anthropic and paying to rebuild its cache each time. Speed never moves a session either: a warm cache is cheaper, and usually faster, than any other route.

Each gateway process learns speeds from its own traffic. The console's Backends page shows them per model (first token, tokens per second).

Which replica of a GPU deployment. Each replica has its own KV cache. When the gateway can reach replicas one by one (SkyPilot's clusters, Kubernetes pods, or a static server's static_urls), it prices each with the same formula, at that replica's load and with the share of the session's prefix that replica probably still holds, and sends the request to the cheapest:

The share still held comes from vLLM's KV events (serve.kv_events), else an estimate from the replica's KV-cache metrics (what it has written since the session's last turn against what it had free), else the cache TTL (04). Behind a load balancer that doesn't know sessions, it's divided by the number of replicas. A replica the gateway can't connect to is skipped for 60 s, and the deployment's endpoint is used.

When a backend fails or a model refuses

The gateway reads the start of every stream, up to its first content, before passing it on. So an error that arrives after a 200 still goes to the next source, and nothing reaches the client twice. Once content has started, an error is passed through: switching then would repeat output. The ledger records that request with the provider's error and status, and the tokens it billed. A too-long prompt isn't counted against the backend, and with X-MeritOrder-Backend set it isn't re-decided.

How long a failing backend or model is skipped:

Failure Skipped For
Over capacity (429, 503, 529) That model on that backend The provider's Retry-After if it sends one, else 10 s doubling; at most 5 min either way. Still tried as a last resort
Model or deployment not found (404) That model on that backend 5 min, doubling to 1 hour while it stays missing (a model not deployed there yet is checked less and less often). Turn a backend off in .env (MERITORDER_BEDROCK=false, MERITORDER_FOUNDRY_CLAUDE=false) until its models exist
Credentials rejected (401, 403) The backend 1 min doubling to 10 min
Anything else (5xx, timeouts, network) The model (408, 409, 425, 500) or the backend (402, 502, 504, network) After 3 in a row: 5 s doubling to 60 s. A Retry-After on a retryable error (not 402) applies at once, up to 5 min

When something starts being skipped, an alert goes to the console's "needs attention" list, the log, and MERITORDER_ALERT_WEBHOOK_URL. It says why and where its traffic goes meanwhile. That's at most once per backend and model every 30 minutes, with a second alert when it works again. The Backends page shows what's skipped and for how long. meritorder_failovers_total{backend,status} counts every failed attempt except bad requests (other 4xx and too-long prompts), and responses served after one carry X-MeritOrder-Failed-Over: backend/model status (or prompt too long).

A request gets at most max_attempts (3) tries in all: failovers, moves to a bigger window, and refusal retries count; asking a route again for what its credit covers (HTTP 402) doesn't, and neither does sending a request to a deployment's endpoint after its replica couldn't be reached. Once a stream has started sending content to the client, a failure can't be retried: the client gets an error event, and the partial usage is still recorded.

When GPUs start, scale, and stop

The capacity controller (meritorder controller) runs every 60 s and wakes within 2 s when an admin changes a GPU control. It needs Postgres, and only one is active at a time (a Postgres advisory lock); a second one stands by.

The state machine (per deployment):

Transition Exactly when
start Wanted ≥ 1 continuously for 10 min and not in a cooldown. At once when an admin pins replicas (ignoring any cooldown from before the pin) or min_replicas > 0 (once any cooldown is over)
ready The replicas answer /v1/models
failed, timed out The start call fails, every replica's SkyPilot launch fails (or a cluster dies before vLLM was ever ready), Kubernetes refuses the pods for good (a quota or policy, an image that can't be pulled, a missing Secret, vLLM crashing three times, credentials the cluster rejects, the resource deleted outside Merit Order), or 45 min pass; the replicas are shut down and the deployment cools down for 30 min. stopped (while starting) An admin stop, Stop all GPUs, the GPU budget, or a fleet cap: provisioning is cancelled at once

When a GPU is full

How "full" is measured. Two signals; a backend is saturated when either reaches 100%:

Signal Source How fresh
vLLM's own load: KV-cache use, pushed to 100% by ~10 waiting requests The controller reads /metrics once per cycle Up to one cycle (60 s) old
Requests in flight ÷ (max_concurrency × replicas) Every gateway counts its own requests to the backend and publishes the count to Redis every 2 s Live for this gateway, ≤ 2 s for others

The second signal only exists when the backend sets max_concurrency (vLLM's --max-num-seqs, or what its KV cache fits). Without it, a burst can pile up in vLLM for up to a minute before the gateways notice. Set it.

Where requests wait. Merit Order has no queue of its own, in Redis or anywhere else: LLM calls are interactive and streaming, so the gateway forwards each request at once and holds the connection open. The only queue is vLLM's scheduler, on the GPU.

Waiting requests are in-flight requests beyond max_concurrency × replicas; without max_concurrency, the controller's last count of vLLM's waiting requests is used. When that count is more than 5 minutes old (the controller stopped, say), every request the gateways have in flight there counts as waiting, so the bound still holds; it may then turn requests away before vLLM's queue is really full. Meanwhile the controller sees the demand and adds replicas (after scale_up_after_minutes, up to max_replicas).
